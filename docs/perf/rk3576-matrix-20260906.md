# RK3576 targeted bench — zh/en cells of the C multilingual matrix (2026-09-06)

`docs/specs/p-voice-split-multilingual-spec.md` §3: "组件有实测，组合待测" for
the RK3576 zh/en cells before this run. This measures the (language, device)
cells the resolver actually produces — `configs/matrix/language_device.yaml` +
`tools/resolve_profile.py` — deployed via the `conversational_voice_ai` package's
own docker-compose on fleet device `cat-remote` (RK3576, LubanCat-3 form
factor), reusing the already-pulled image and model volumes. No new image was
pulled; no volume was deleted.

Device: fleet `cat-remote`. Software: openvoicestream commit `a0b043a6`
(branch `feature/language-device-resolver`). Container image:
`openvoicestream:rk-20260903.10` (`sha256:fdc480da3061...`), already cached on

## Method

- ASR WER/CER: `bench/perf/asr_stream_ws_bench.py` against `bench/perf/corpus`
  — the existing FLEURS-derived (CC BY 4.0) corpus already used for
  `docs/perf/whisper-cross-device-20260827.md`, sha256-verified on-device
  (`fetch.py --verify`, 20/20 ok). **N=5 short + 5 long per language (10 per
  language)**, not a fresh 20-clip Common Voice download — reused per "OVS
  tests 语料里若已有就复用" rather than pulling a new dataset. `--host
  127.0.0.1:8621`, default `--chunk-ms 250`, non-realtime feed, 1.5-3s delay
  inserted between files by a small patch to the bench script
  (`SessionLimiter` effective_limit=1 rejected back-to-back connections
  without a gap; the fix is a `time.sleep()` between corpus items, not a
  server change).
- TTS RTF: 5 sentences per language via `POST /tts`, reading the server's own
  `x-rtf` / `x-inference-time` / `x-audio-duration` response headers directly
  (no separate stopwatch).
- V2V latency: `bench/perf/measure_v2v_unified.py --host 127.0.0.1:8621 --tts`,
  1 short corpus file per language, 1 warmup + 5 measured runs.

### V2V echo-mode caveat (both cells)

Neither `agent` (the real dashscope LLM loop) nor `OVS_V2V_SERVER_LOOP` was
exercised: `EdgeLLMBackend` hardcodes `api_key="edge-llm"` with no env override
for a real bearer token
(`server/core/edge_llm_backend.py`), so pointing `EDGE_LLM_BASE_URL` at
dashscope inside the speech container would fail auth. The V2V numbers above
are ASR-final-text echoed straight into TTS (the harness's own
`--tts`-without-`--server-loop` mode) — they measure ASR+TTS pipeline latency,
not a real conversational round trip.

Root cause found for a real bug along the way: in single-utterance mode
(no `--multi`), the deployed server's `/v2v/stream` handler sets
`state["asr_session_closed"] = True` immediately on the first `asr_final` and
closes the socket before the client's injected `{"type": "text"}` /
`{"type": "tts_flush"}` messages can reach the TTS buffer — the container log
shows `v2v stream closed` a few ms after the final with zero Matcha/TTS
activity. Worked around here with `--multi 2` (same wav replayed with an 800ms
gap keeps the session open through the TTS round trip), at the cost of NPU
contention from the second utterance's concurrently-arriving audio — a real
caveat on the absolute latency numbers, not corrected for.

"完整回复"（last TTS frame / `tts_done`) was not captured: `measure_v2v_unified.py`
only timestamps the first PCM frame, not completion. Not estimated here to
avoid mixing a derived number into a measured table — the TTS RTF above turns
into a rough add-on estimate the reader can compute (first-frame latency +
reply_duration x RTF) but that is not the same as a measurement.

## Addendum 2026-09-06 (2nd pass): dictation-mode env override — hypothesis falsified

The long-form CER (84.06% zh / 63.38% word-error en) was hypothesized to be
caused by `rk3576-default`'s low-latency conversational settings —
`ASR_MAX_NEW_TOKENS=64` and `ASR_FINAL_STOP_ON_PUNCT=1` — cutting the decoder
off after the first clause. To test this, the same stack was redeployed with
only those two values changed via env override (not the profile file):

```
services:
  speech:
    environment:
      ASR_FINAL_STOP_ON_PUNCT: "0"
      ASR_MAX_NEW_TOKENS: "256"
      RK_ARTIFACT_CONTRACT_STRICT: "0"
```

`RK_ARTIFACT_CONTRACT_STRICT=0` was required in addition to the two requested
vars: `server/core/rk_artifacts.py::_validate_runtime_contract` hard-fails
startup (`RKArtifactError` -> `sys.exit(1)`) when the runtime env diverges from
the artifact set's `runtime_contract.env`, and this artifact set's contract
pins exactly `ASR_MAX_NEW_TOKENS=64` / `ASR_FINAL_STOP_ON_PUNCT=1`. Without the
strict-mode flag the container crash-looped (confirmed: 9 restarts, `SystemExit: 1`,
`server.core.rk_artifacts.RKArtifactError: ... got '256', expected '64'; ...
got '0', expected '1'`) and never reached `/health`. With the flag it becomes a
logged warning and the server starts. This is an existing, documented env
toggle in the code (not a profile-file edit).

**Env-applied evidence** (container log at boot):
```
[WARNING] server.core.profile_loader: Profile rk3576-default wants ASR_MAX_NEW_TOKENS=64 but env overrides to 256
[WARNING] server.core.profile_loader: Profile rk3576-default wants ASR_FINAL_STOP_ON_PUNCT=1 but env overrides to 0
[ERROR] server.main: RK profile contract INVALID: ... mismatches=ASR_MAX_NEW_TOKENS,ASR_FINAL_STOP_ON_PUNCT
[WARNING] server.core.rk_artifacts: RK artifact runtime contract mismatch ... Details: ASR_MAX_NEW_TOKENS: got '256', expected '64'; ASR_FINAL_STOP_ON_PUNCT: got '0', expected '1'
[INFO] server.core.model_downloader: All models for mode 'rk' are ready.
[INFO] server.main: Speech service ready.
```
`docker inspect --format '{{.State.Health.Status}}'` -> `healthy`, `RestartCount: 0`.

### Result: identical transcripts, identical WER/CER

| Mode | zh short CER (n=5) | zh long CER (n=5) | en short WER/CER (n=5) | en long WER/CER (n=5) |
|---|---|---|---|---|
| Conversational (`ASR_MAX_NEW_TOKENS=64`, `STOP_ON_PUNCT=1`) | mean 29.09% | mean 84.06% | mean 16.95% / 10.16% | mean 63.38% / 62.58% |
| Dictation (`ASR_MAX_NEW_TOKENS=256`, `STOP_ON_PUNCT=0`) | mean 29.09% | mean 84.06% | mean 16.95% / 10.16% | mean 63.38% / 62.58% |

Every per-file transcript in the dictation-mode run is byte-identical to the
conversational-mode run (e.g. `zh_long_01` still finalizes as "这并不是告别。"
after 1 server message, `en_long_03` still finalizes as "To prevent possible
infection of others." after 43 messages taking 7.5s). Raw JSON lines for both
runs are in this file's git history / session transcript.

**The hypothesis is falsified: `ASR_MAX_NEW_TOKENS` and
`ASR_FINAL_STOP_ON_PUNCT` are not the cause of the long-form truncation on
this profile.** The `messages` count (1-3 server messages for most long files,
`eos_to_final_ms` around 2s even for 10-20s audio) points instead at VAD-based
endpoint detection (`OVS_VAD_BACKEND=silero`, `VAD_ENDPOINT_SILENCE_MS=400`,
`QWEN3_ASR_FRONTEND_EOU_MIN_AUDIO_S=2.5`) treating the first natural pause in
the audio as end-of-utterance and finalizing before the rest of the clip is
ever fed to the decoder — a streaming front-end behavior, not a decoder token
budget or punctuation-stop setting. **This is a "待办"（open item), not
something this bench fixes**: identifying and testing the actual VAD/endpoint
parameters that would let a true-streaming session survive a mid-utterance
pause is separate engineering work, out of scope here.

Short-utterance truncation (2/5 files: `zh_short_03`, `zh_short_05`) persists
unchanged in dictation mode too, for the same reason — it is not an
edge-of-decoder-budget effect at all.

containers untouched; `.env.voiceC-dictation` renamed to
`.env.bak-voiceC-dictation`; `df -h /` unchanged at 6.1G free.

## Addendum 2026-09-06 (3rd pass): offline `POST /asr` separates model capability from VAD-endpoint behavior

To isolate "what the model can transcribe" from "when the streaming VAD
decides an utterance ended," the same 10 zh + 10 en corpus files were sent
through `POST /asr` — the whole-file offline endpoint already used for
`retail_voice_local`'s `verify_asr.yaml` offline check
(`~/project/sensecraft_voice/evaluation/runs/2026-09-06-retail-local-rk3576/results.md`
§3). This endpoint (`server/main.py::asr` / `_asr_impl`) reads the entire
uploaded file into memory and runs `execute_asr()` once — no VAD, no
streaming, no `ASR_FINAL_STOP_ON_PUNCT`/`ASR_MAX_NEW_TOKENS` streaming-loop
logic in the path at all — so it exists and accepts long audio on this image
without needing the 1500ms-VAD-threshold fallback path.

**Interface/params used, and evidence it is the offline path**: `curl -X POST
'http://127.0.0.1:8621/asr?language=zh' -F 'file=@zh_long_01.wav'` →
`{"text":"这并不是告别，这是一个篇章的结束，也是新篇章的开始","language":"zh","backend":"rk:qwen3_asr_rk","rtf":0.388,"enc_ms":1835,"llm_ms":2186}` —
the full two-clause reference text comes back in one response with `enc_ms`/`llm_ms`
timing fields specific to the non-streaming `execute_asr()` path (the
`/asr/stream` WebSocket path never returns these fields; it returns
`partial`/`final`/`endpoint` frames instead). Deployment: `speech` only,
`docker-compose.rk3576.yml` + `cat-rk3576-async-sync.override.yml`,
`OVS_PROFILE=rk3576-default` (default, unchanged) — the streaming-only
`ASR_MAX_NEW_TOKENS`/`ASR_FINAL_STOP_ON_PUNCT` values are irrelevant to this
path so were left at the shipped default.

New script: `bench/perf/offline_asr_bench.py` (reuses `_err_rate` /
`_char_err_rate` from `asr_stream_ws_bench.py` for identical scoring
normalization).

### Result: model capability (offline, no VAD endpoint)

| Metric | N | Value |
|---|---|---|
| zh short CER | 5 | mean 1.05% (4/5 exact match; zh_short_03 5.3%) |
| zh long CER | 5 | mean 9.62% (3/5 exact; zh_long_02/03 have real errors — digit-to-hanzi normalization mismatches and two garbled words, not truncation) |
| en short WER / CER | 5 | mean 3.65% / 1.11% |
| en long WER / CER | 5 | mean 6.99% / 4.16% |

Every long file now returns its full multi-clause reference content (compare
zh_long_01: streaming path finalized "这并不是告别。" after 1 message; offline
path returns "这并不是告别，这是一个篇章的结束，也是新篇章的开始" — the whole
sentence, 0% CER). The residual long-form CER/WER here is real recognition
error (numeral normalization: "15米"→"十五米" vs a raw-digit reference; a
mis-heard word in zh_long_03; "3:2"→"three to two" in en_long_05) — not VAD
truncation.

### Three-row picture (per language, per length bucket)

| Mode | zh short | zh long | en short (WER/CER) | en long (WER/CER) |
|---|---|---|---|---|
| Conversational (streaming, 400ms VAD, `ASR_MAX_NEW_TOKENS=64`/`STOP_ON_PUNCT=1`) | 29.09% CER | 84.06% CER | 16.95% / 10.16% | 63.38% / 62.58% |
| Dictation (streaming, 400ms VAD, `ASR_MAX_NEW_TOKENS=256`/`STOP_ON_PUNCT=0`) | 29.09% CER (identical) | 84.06% CER (identical) | 16.95% / 10.16% (identical) | 63.38% / 62.58% (identical) |
| **Offline `/asr` (model capability, no VAD endpoint)** | **1.05% CER** | **9.62% CER** | **3.65% / 1.11%** | **6.99% / 4.16%** |

**Conclusion**: the gap between row 1/2 and row 3 is entirely the streaming
VAD endpoint finalizing on the first pause — confirmed, not just theorized,
because bypassing it (row 3) recovers the model's real accuracy. **A long
sentence ending at the first pause is the streaming endpoint design, not a
recognition error** — the conversational-mode numbers describe when a
real-time session decides to reply, not what the decoder is capable of
transcribing when given the whole clip.

## Addendum (2026-09-06, after this run): the emitted key set changed

The resolver output captured verbatim above is the key set as of commit
`a0b043a6`. It has since been narrowed, because a review found that
`LANGUAGE`, `ASR_LANGUAGE`, `TTS_LANGUAGE`, `OVS_AUDIO_INPUT_CHANNELS` and
`OVS_AUDIO_MONO` had zero read points in `server/`, `services/`, `scripts/`
and `deploy/` — the language selection stopped at the profile and never
reached the ASR/TTS backends.

What changed (see the README "What it emits, and who reads it" table):

- added `OFFLINE_ASR_LANGUAGE` (`server/core/voxedge_backend_config.py:268`)
  and `WHISPER_LANGUAGE` for `en`/`zh` only
  (`server/core/voxedge_backend_config.py:944`);
- `ASR_LANGUAGE` / `TTS_LANGUAGE` kept, and the agent config template now
  reads both, so they land in the per-session v2v config — the only language
  knob the RK Qwen3-ASR backend has (`voxedge rk/asr.py:517`,
  `transcribe(..., language="auto")`);
- dropped `LANGUAGE` (POSIX locale collision) and the two `OVS_AUDIO_*` keys
  (no consumer; mono is enforced by `mic_channel_select` plus the segmenter's
  downmix).

The numbers in this document are unaffected: no measurement here depended on
any of the removed keys, and `OVS_PROFILE` — which selected the models that
were measured — is unchanged. What did change is that the zh cell now pins the
ASR language instead of leaving it at per-utterance language ID, so a repeat
of this bench should be expected to differ on Chinese short-utterance results
rather than to reproduce them exactly.

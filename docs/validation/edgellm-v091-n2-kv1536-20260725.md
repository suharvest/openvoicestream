# TensorRT-Edge-LLM v0.9.1 N=2 validation

Date: 2026-07-25  
Device: Jetson Orin NX 16GB, JetPack 6.2, CUDA 12.6, TensorRT 10.3, SM87

## Outcome

N=2 is qualified only as an isolated, same-model capacity mode. It must not
replace the production all-resident N=1 profile.

| Scope | Correctness/stability | Low-latency result | Decision |
| --- | --- | --- | --- |
| Qwen3-ASR batch 2 | pass, 50/50 offline and 50/50 streaming | pass | enable N=2 when GDN is stopped or capacity is explicitly reserved |
| Qwen3-TTS Base worker batch 2 | pass, 50/50 cancel/keep/recovery | pass at worker layer | retain as an opt-in artifact |
| Qwen3-TTS Base HTTP batch 2 | pass, 30/30 and stable PCM | fail 1.5x TTFA gate; observed 1.71x | optimize service path before making it a low-latency default |
| Qwen3.5-4B GDN+MTP two clients | 50/50 responses correct | no token-stream overlap | capacity remains one active generation; queue the second request |
| ASR N=2 plus TTS N=2 | 5/5 functionally correct | cross-component scheduling blocks ASR behind long TTS | do not admit both stages simultaneously |
| ASR N=2 plus TTS N=2 plus GDN | OOM and GDN restart | fail | unsupported on Orin NX 16GB |

The production recommendation remains:

- keep ASR, TTS Base and GDN resident with batch 1;
- use same-stage N=2 only in an explicit isolated profile;
- serialize ASR and TTS stages for latency;
- keep GDN at one active generation;
- stop GDN before selecting the voice N=2 profile.

## Qwen3-ASR N=2

### Offline service requests

Two different samples were issued together on every round:

- Chinese: `今天天气真好。`
- English: `The weather is beautiful today.`

Results:

- 50/50 pairs passed with exact expected content and no cross-talk;
- Chinese p50/p95: 226.19/227.81 ms;
- English p50/p95: 226.32/228.03 ms;
- immediate single-request recovery p50/p95: 108.32/109.32 ms;
- no CUDA, TensorRT, Myelin, worker-exit or container error.

Three simultaneous HTTP `/asr` requests did not enforce the expected
fail-fast capacity contract. All three returned 200 and the extra request was
queued, taking about 334 ms. The engine N=2 result is valid, but the HTTP
oversubscription behavior must be fixed separately if 4429 rejection is
required.

Evidence:
`/home/harvest/validation/v091-n2-kv1536-20260725/asr-service-n2-soak50.json`.

### WebSocket streaming

The test used real-time 250 ms PCM chunks and `vad=none`, so client EOS rather
than an internal silence split defines the final transcript.

- 50/50 pairs passed;
- 100/100 lanes emitted a partial before client EOS;
- first partial p50/p95: 500.98/501.28 ms;
- EOS-to-final p50/p95: 111.78/117.21 ms;
- the two streaming sessions overlapped for about 2.107 s each round;
- final Chinese and English content remained correct.

With the default server VAD, the synthetic TTS samples contain enough internal
silence to split early (`今天天气。` / `The weather.`). That result is a VAD
segmentation effect, not an N=2 cross-talk failure.

Evidence:
`/home/harvest/validation/v091-n2-kv1536-20260725/asr-stream-n2-soak50.json`.

## Qwen3-TTS Base N=2

### Direct worker

The strengthened gate requires both streams to emit their first chunk before
the other stream ends. It also checks deterministic PCM, cooperative
cancellation and immediate recovery.

- 50/50 rounds passed;
- both full concurrent streams had TTFA about 562 ms and total time about
  3.968 s;
- cancel and keep TTFA p50/p95: 564.54/570.13 ms and 564.22/570.21 ms;
- cancellation acknowledgement p50/p95: 7.85/8.02 ms;
- kept-stream total p50/p95: 2,400.53/2,407.68 ms;
- recovery TTFA p50/p95: 307.28/307.58 ms;
- every kept/recovery PCM matched its single-request baseline byte-for-byte;
- no CUDA/TensorRT errors.

Evidence:
`/home/harvest/validation/v091-n2-kv1536-20260725/tts-worker-n2-soak50-final.json`.

### HTTP streaming

The service gate ran 30 two-client bursts while ASR batch 2 remained resident.

- 30/30 bursts returned PCM;
- pre/post stress PCM MD5 was identical;
- no CUDA errors or container restart;
- steady N=1 TTFA p50/p95: 1,368.9/1,694.6 ms;
- N=2 combined TTFA p50/p95: 2,346.5/2,671.8 ms;
- N=2/N=1 p50 ratio: 1.71x.

The functional gate passes, but the low-latency acceptance limit is 1.5x.
Service-side buffering, request cancellation and scheduling therefore remain
optimization targets. Worker-layer N=2 performance alone is not sufficient to
promote the HTTP profile.

Evidence:
`/home/harvest/validation/v091-n2-kv1536-20260725/tts-service-results/qwen3_base_n2_stability_20260725_042842.json`.

## Cross-component scheduling

Five rounds started two full TTS requests and two ASR requests together.
Every text and WAV was correct and the container did not restart. However:

- TTS requests took about 2.82-6.53 s depending on prompt length and lane;
- ASR requests took about 6.52-6.65 s;
- ASR completion followed the longest TTS lane by roughly its normal
  0.23-second compute time.

The request windows overlap, but useful ASR compute is scheduled behind TTS.
Admitting four simultaneous voice requests therefore increases latency without
providing the intended interactive concurrency.

Evidence:
`/home/harvest/validation/v091-n2-kv1536-20260725/voice-cross-component-n2-smoke5.json`.

## GDN+MTP two-client behavior

Fifty two-client SSE rounds returned correct content with no runtime error:

- idle single-request TTFT p50: 71.70 ms;
- two-client combined TTFT p50/p95: 142.03/209.71 ms;
- token-stream overlap: 0/50 rounds.

One request consistently starts at about 74 ms, while the second starts at
about 209 ms after the first stream finishes. This is stable service queuing,
not true GDN N=2 execution.

Evidence:
`/home/harvest/validation/v091-n2-kv1536-20260725/gdn-n2-soak50.json`.

## Whole-device limit and recovery

With GDN resident, the voice N=2 service could load ASR batch 2. Triggering the
TTS batch-2 lazy load then produced:

- cold TTS TTFA: 23.82 s;
- `MemAvailable`: about 398 MiB;
- swap used: about 2.66 GiB at the observation point;
- ASR worker removed from residency;
- voice container `OOMKilled=true`;
- GDN restarted repeatedly.

This is a hard fail for full residency. No additional N=2 pressure was applied.
The temporary container was stopped and the validated production N=1 services
were restored.

Final recovery gate:

- production voice `/readyz`: ready;
- both ASR batch-1 and TTS batch-1/KV1536 workers resident;
- GDN healthy;
- one complete TTS/GDN then ASR/GDN overlap round passed;
- GDN restart count remained unchanged during the recovery round;
- voice restart/OOM: `0 / false`.

Evidence:
`/home/harvest/validation/v091-n2-kv1536-20260725/production-n1-restored-smoke.json`.

## Follow-up optimization order

1. Reduce the Qwen3-TTS HTTP TTFA gap between the direct worker (~0.56 s at
   N=2) and service path (~2.35 s p50 at N=2).
2. Make `/asr` oversubscription obey an explicit queue-or-4429 product
   contract.
3. Keep cross-component ASR/TTS admission stage-aware so long TTS work cannot
   starve ASR finalization.
4. Treat true GDN N=2 as unsupported until NVIDIA/runtime execution contexts
   can overlap safely; do not advertise queued requests as concurrent
   generation.
